## 1. 项目结论

**DevFlow Agent 是一个已完成端到端闭环、可重复演示、具备真实大模型与跨电脑知识检索能力的企业级可控 Agent MVP。**

它不是普通聊天机器人，也不是单次 Function Calling 示例。项目围绕“研发故障调查与变更协同”完成了以下闭环：

1. DeepSeek 识别调查意图并生成结构化计划。
2. LangGraph 按有向工作流调度 7 个调查步骤。
3. 所有计划工具统一经 MCP Client 调用 4 个 MCP Server。
4. Knowledge MCP 跨电脑调用真实 Enterprise Knowledge Copilot，并把 Citation 转成可信 Evidence。
5. Agent 综合指标、日志、知识和代码变更，生成带证据的复盘报告。
6. 高风险写操作必须经过人工审批、角色与参数哈希校验。
7. 任务状态、事件与幂等记录持久化，异常中断后可以恢复。
8. 自动化测试、Golden Set 和五维 Evaluation 对结果进行回归验收。

当前适合用于 AI 应用开发、Agent 工程、RAG 应用、AI 后端平台等岗位的作品集和项目面试。它仍是本地/局域网 MVP，不应包装成已经在真实企业生产环境上线的系统。

## 2. 一句话项目定位

### 简历标题

**DevFlow Agent｜企业研发故障调查与变更协同 Agent**

### 一句话介绍

基于 LangGraph、DeepSeek、MCP 和 FastAPI 构建可恢复、可审批、可审计、可评测的企业 Agent，跨监控、日志、知识库与代码变更完成故障调查，并在人工确认后执行受控写操作。

### 项目组合边界

- Enterprise Knowledge Copilot 负责：RAG、检索、Rerank、Citation 和 ACL 过滤。
- DevFlow Agent 负责：Planning、Skill 编排、工具调用、证据综合、审批、执行、恢复和评测。
- 一句话说明：**RAG 提供有出处的知识，Agent 基于知识采取受控行动。**

## 4. 技术架构背书

### 4.1 当前真实技术栈

- AI/Agent：LangGraph、DeepSeek V4 JSON Output、Pydantic Structured Output。
- 服务端：Python、FastAPI、官方 MCP Python SDK 2.x。
- Agent 能力：Intent Detection、Structured Planning、Skill Selection、Reflection、HITL、Evaluation。
- 数据与状态：SQLite WAL、任务 Checkpoint、审计事件、幂等记录。
- 知识集成：远程 HTTP Retrieval、ACL 上下文传播、Citation Contract、Fixture 降级。
- 前端：Next.js、TypeScript。
- 可观测性：Prometheus Metrics、OpenTelemetry API 基础 Span。
- 工程化：Pytest、Golden Set、Dockerfile、Docker Compose 配置。

### 4.2 设计亮点

#### 确定性骨架 + 有界 LLM

LLM 负责意图识别、结构化规划和证据推理；工具目录、步骤依赖、风险级别、角色、审批和状态转移由代码控制。模型超时、不可用或输出越界时回退到确定性逻辑，因此系统不会因为模型输出不稳定而完全失去执行能力。

#### MCP 不是展示层，而是执行主链

Runtime 默认使用 `tool_mode=mcp`，主任务的 7 个计划工具全部通过 MCP Client 路由。客户端处理超时、有限重试、响应结构校验和调用指标；高风险写操作在 Gateway 和 Server 两侧重复校验。

#### Evidence-first

每条关键结论绑定 Evidence ID、来源 URI 和内容哈希。远程检索结果必须通过严格 Citation Contract；知识正文始终视为不可信数据，不能覆盖系统指令、权限或审批规则。

#### 写操作安全

`create_issue` 需要同时满足角色、风险、人工批准和精确参数哈希；写入使用幂等键。即使外部响应丢失后发生重试，也不会重复创建同一资源。

#### 可恢复与可评测

任务状态按节点持久化到 SQLite。进程中断后可以通过 Resume API 从已保存状态继续。Golden Set 固定使用确定性 Planner，避免真实 LLM 波动破坏回归基线；真实 LLM 另做集成验收。

## 9. STAR 面试回答模板

### Situation

研发故障调查需要在监控、日志、历史事故、Runbook 和代码变更之间反复切换。普通 RAG 只能回答知识问题，自由 Agent 又可能产生越权写入、无证据结论和不可恢复等风险。

### Task

我需要设计一个既能利用大模型处理不确定调查路径，又能满足企业系统对权限、审批、审计、幂等和可回归测试要求的 Agent MVP。

### Action

我采用 LangGraph 构建确定性状态机，让 DeepSeek 只负责意图、计划和证据推理；用 Pydantic 和 Policy Catalog 校验模型输出；将 7 个工具统一接入 MCP Client；为每条结论建立 Evidence ID、来源 URI 和内容哈希；对写操作加入角色、人工审批、参数哈希、Server 二次校验和幂等保护；使用 SQLite 持久化任务、事件和写入记录；最后建立 43 项测试、15 条 Golden Set 与五维 Evaluation，并完成跨电脑真实 Knowledge API 联调。

### Result

项目实现了从自然语言目标到调查、取证、报告、审批和模拟 Issue 的完整闭环。回归用例达到 15/15，真实联合任务得到 9 条证据，其中 3 条来自远程知识库，内置评测为 100/A+；同时验证了超时、中断、响应丢失、越权和 Prompt Injection 场景。

## 10. 高频面试问题与回答要点

### 为什么不用纯 ReAct Agent？

企业写操作不能依赖模型自由决定状态转移。我把权限、审批、依赖、幂等和恢复放在确定性 Runtime 中，只把真正需要语义判断的意图、规划和证据综合交给 LLM，在灵活性与可控性之间取平衡。

### 为什么使用 MCP？

MCP 把 Agent Runtime 与工具实现解耦，统一工具描述、参数和返回结构。这个项目不是只启动一个 MCP Demo，而是让 7/7 主链工具都经过 MCP Client，同时在 Gateway 和 Server 两侧执行安全检查。

### 模型输出不合法怎么办？

DeepSeek 使用 JSON Output，结果先经过 Pydantic，再经过工具目录、依赖和风险策略校验。超时、解析失败或计划越界时自动回退到确定性 Planner，保证演示和回归可继续。

### 如何防 Prompt Injection？

用户输入和检索内容都被视为数据，不能直接改变角色、权限和审批状态。远程 Citation 必须带不可信内容标记；即使文档要求“忽略审批”，写工具仍需通过代码层角色、批准状态和精确参数哈希校验。

### 响应丢失为什么不会重复创建 Issue？

写操作先使用稳定幂等键预留记录，成功结果持久化。若外部系统已执行但客户端未收到响应，重试会查询同一幂等记录并返回已有结果，而不是再次创建。

### 任务进程中断后如何恢复？

Runtime 在节点级把 AgentState 持久化到 SQLite，保留计划、步骤状态、证据、审批和事件。服务恢复后通过 Resume API 读取持久状态，从尚未完成的步骤继续执行，而不是从头重复整条任务。

### 为什么 Golden Set 不调用真实 LLM？

真实模型输出和延迟会波动，不适合作为每次提交的稳定回归基线。因此 Golden Set 固定使用确定性 Planner + MCP Client；真实 DeepSeek 单独做集成验收，既保证回归可重复，也验证真实模型链路。

### 当前最大的生产化差距是什么？

当前仍缺生产身份与授权体系、PostgreSQL/Redis 状态层、远程 MCP 传输、真实监控/Git/Issue 系统、完整 Trace 后端和 SLO。我的简历只把它定义为企业级可控 Agent MVP，不宣称已经生产上线。
