# Enterprise AI Agent Platform 面试手册

> 适用项目：DevFlow Agent — 企业研发故障调查与变更协同平台  
> 使用方法：先掌握前 16 章的回答骨架，再用第 17 章的 50 道追问做口述演练。回答时先讲结论，再讲本项目证据，最后讲权衡。

## 1. 什么是 Agent

**面试官关注点**

是否能区分 LLM、聊天机器人和 Agent，是否理解“目标—状态—行动—观察—终止”的闭环。

**标准回答**

Agent 是以目标为驱动、能够感知上下文、维护状态、选择行动、调用工具并根据观察继续决策的系统。LLM 是其中的决策组件，不等于整个 Agent。DevFlow Agent 中，LLM 参与意图、计划候选和证据综合，LangGraph、Policy、Tool、Memory、Approval 和 Evaluation 共同构成完整系统。

**深入扩展**

企业 Agent 的关键不在“自主程度最大”，而在“能在不确定任务中做有限决策，同时让权限、副作用、成本和过程可控”。因此本项目采用有界 Agent，而非无限 ReAct 循环。

## 2. Agent 和 RAG 的区别

**面试官关注点**

是否把 RAG 和 Agent 混成一套框架，能否解释两个项目为何不重复。

**标准回答**

RAG 解决知识增强：从外部知识源检索证据，帮助模型生成有依据的回答。Agent 解决任务执行：根据目标规划步骤、选择 Skill/Tool、处理结果和失败，并可能产生受控副作用。Knowledge Copilot 提供带引用知识；DevFlow Agent 决定何时调用知识、如何与指标/日志/Git 证据组合，以及审批后做什么动作。

**深入扩展**

RAG 可以是 Agent 的一个 Tool 或 Skill，但 Agent 不能代替文档摄取、检索评测和引用治理；两个系统保持独立服务边界更易演进。

## 3. Agent 架构

**面试官关注点**

能否从模型之外讲清状态、编排、工具、记忆、治理和可观测性。

**标准回答**

本项目分四层：交互层负责请求、进度、证据和审批；Runtime 层负责状态图、Planning、Skill 和 Tool；能力层通过 MCP 与 Knowledge API 连接监控、数据、Git 和知识；治理层负责身份、权限、审批、Memory、Trace、指标和 Evaluation。模型通过 Gateway 调用，不能直接持有企业系统权限。

**深入扩展**

运行时所有模型输出都应被视为候选数据，必须经过 Schema 与 Policy；外部返回内容也按不可信输入处理。

## 4. LangGraph 原理

**面试官关注点**

是否理解 State、Node、Edge、Checkpointer、Interrupt，而不只是会调用 API。

**标准回答**

LangGraph 把 Agent 建模为状态图：State 是节点共享的结构化状态，Node 读取 State 并返回增量更新，Edge 决定下一节点，Checkpointer 在步骤间保存快照，Interrupt 支持暂停等待人工输入后恢复。DevFlow 用它实现有界重规划、审批暂停和故障恢复。

**深入扩展**

副作用必须放在可追踪的节点/任务中并设计幂等；否则恢复时重放可能重复创建 Issue。State 只存可序列化事实和引用，避免大对象与密钥。

## 5. Workflow Agent

**面试官关注点**

是否能平衡确定性和灵活性。

**标准回答**

Workflow Agent 是“固定控制骨架中的有限智能决策”。本项目固定 Intent、Plan Validation、Policy、Approval、Reflection 和 Final 的治理顺序；模型只在受限候选中规划 Skill 和工具。这样既能根据证据改变调查路径，又能保证副作用不会绕过审批。

**深入扩展**

如果任务分支可穷举，就不需要 Agent；可以直接用普通 DAG。Agent 的引入必须由运行时不确定性证明。

## 6. Planner 设计

**面试官关注点**

是否有结构化计划、校验器、依赖、成功标准和失败策略。

**标准回答**

Planner 输入是解析后的意图、权限过滤后的 Skill 摘要、预算与策略；输出符合 JSON Schema 的 DAG，每步包含 skill_id、depends_on、success_criteria、risk 和 requires_approval。随后由确定性 Validator 检查 Schema、无环、权限、步骤上限和最终产物可达，Planner 自己不执行工具。

**深入扩展**

规划和参数生成分开：计划只决定做什么，具体 SQL/工具参数在执行步骤按 Tool Schema 生成，缩小危险自由文本面。

## 7. Reflection 机制

**面试官关注点**

是否把 Reflection 误解为“再问一次模型觉得好不好”。

**标准回答**

Reflection 是对计划完成度、证据覆盖和工具结果的一次受限质量门。规则先检查每个成功标准、Evidence ID、引用可访问性和失败步骤；模型只用于识别可能遗漏或冲突。若缺口可补且预算允许，最多重规划两次，否则输出部分结果和限制。

**深入扩展**

不能让同一个模型既生成又无约束地给自己打分。高风险结论应增加程序校验、独立评审模型或人工复核。

## 8. Function Calling

**面试官关注点**

是否理解模型返回的是结构化调用意图，不是函数已执行。

**标准回答**

Function Calling 让模型根据工具描述生成函数名和结构化参数。应用仍要校验 Schema、身份、授权和业务规则，实际执行函数，再把结果返回模型。它改善参数可靠性，但不自动提供安全、幂等、重试或审计。

**深入扩展**

工具描述要说明正向用途、边界和风险，参数要限制枚举、长度、范围和 `additionalProperties=false`；不要暴露“万能 execute_sql/execute_shell”。

## 9. Tool Calling

**面试官关注点**

能否讲清发现、选择、授权、执行、结果验证完整链路。

**标准回答**

Tool Calling 是应用层完整生命周期：Registry 发现，Skill 缩小候选，模型提出调用，Schema 校验，Policy 决策，人工审批，执行器调用，outputSchema 校验，结果写 Evidence/Trace，最后回到 Agent。模型选择工具不等于获得调用权限。

**深入扩展**

错误应类型化。只对瞬时且可重放的读错误重试；权限或参数错误应直接修复/终止；未知写结果先对账，不能盲重试。

## 10. MCP 协议

**面试官关注点**

为什么使用、Client/Server 职责、与 Function Calling 的区别、安全性。

**标准回答**

MCP 用统一协议把模型宿主连接到工具和上下文。Server 暴露工具、资源或提示模板，Client 完成能力发现、调用、取消和结果处理。本项目用 MCP 解耦监控、Git 和工作区集成，开发用 STDIO，远程集成用 Streamable HTTP；Runtime 仍保留自己的授权与审批。

**深入扩展**

MCP 的 Tool 有 inputSchema 和可选 outputSchema。Server 的工具描述与 annotations 不能被宿主直接信任；身份、租户范围、数据脱敏和用户同意仍需应用实现。

## 11. Skill 系统

**面试官关注点**

Skill 是否只是 Tool 换名，能否发现、加载、版本化和评测。

**标准回答**

Skill 是可复用业务工作流包，包含触发描述、Prompt、输入输出、工具绑定、策略、参考资料、模板和测试；Tool 是一个原子动作。Runtime 先用简短 metadata 匹配 Skill，选中后才加载完整指令，既减少 token，也降低无关内容干扰。

**深入扩展**

企业 Registry 要做权限硬过滤、语义版本、灰度、回滚和评测准入。运行中任务固定 Skill 版本，避免热更新造成不可复现。

## 12. Memory 机制

**面试官关注点**

是否区分工作记忆、长期任务记忆和企业知识，是否考虑污染、隐私和删除。

**标准回答**

Working Memory 是当前 AgentState 和检查点；Episodic Memory 是历史任务摘要、用户明确偏好与反馈；Enterprise Knowledge 由 Knowledge Copilot 管理。PostgreSQL 保存持久状态，Redis 提供锁和热数据，向量索引只用于经过 ACL 的语义检索。

**深入扩展**

不是所有聊天都应长期保存。写长期记忆前要抽取、脱敏、去重和按保留策略处理；记忆检索结果也可能包含 Prompt Injection，必须作为数据而非指令。

## 13. 多模态 Agent

**面试官关注点**

多模态是否服务真实需求，如何控制识别错误。

**标准回答**

本项目只支持与故障调查直接相关的日志/监控截图。视觉模型提取服务名、时间、错误码和日志片段，输出结构化字段与置信度；低置信字段要求用户确认后才进入 Planner。视觉不可用时允许粘贴文本降级。

**深入扩展**

图片中的文本同样可能是恶意指令；OCR 结果与用户文本要标注来源，不能提升为系统指令。

## 14. Agent 安全

**面试官关注点**

是否只会说“加 Guardrail”，能否分层给出控制。

**标准回答**

安全分为身份与授权、输入隔离、工具策略、副作用控制、数据治理和运行限制。具体包括 SSO、RBAC/ABAC、租户过滤、参数 Schema、SQL/路径 allowlist、默认只读、审批、幂等、出站网络限制、脱敏、预算和审计。高风险能力在 MVP 中不注册工具，不能只靠 Prompt 禁止。

**深入扩展**

审批必须绑定具体参数哈希和有效期；参数变化后重新审批。Tool/MCP/Skill 都是供应链入口，需要固定版本和准入审核。

## 15. Agent 评测

**面试官关注点**

是否有任务级、步骤级、安全与系统指标，而非主观看回答。

**标准回答**

评测分 Intent、Planning、Skill/Tool、Execution、Answer、Safety 和 System。指标包括实体 F1、计划有效率、工具/参数准确率、任务完成率、证据覆盖与引用正确率、越权阻断、恢复率、p95 延迟和单任务成本。任何 Prompt、模型、Skill 或 Schema 变化都回放同一 Golden Set。

**深入扩展**

LLM-as-judge 适合评价表达或开放质量，但权限、引用存在性、Schema、重复副作用等必须程序化判断；高风险样本要人工复核。

## 16. 企业 Agent 落地问题

**面试官关注点**

是否理解真正难点在系统集成、治理和运营，而非调用模型。

**标准回答**

主要难点是数据权限、身份映射、系统接口不一致、长任务恢复、写操作责任、可观测性、效果评测、成本延迟和组织采纳。落地应从一个高频、证据可得、风险可控的只读闭环开始，证明价值后再逐步开放写操作和更多 Skill。

**深入扩展**

生产化需要明确 owner、SLO、审计与事故响应；还要允许人随时接管。技术上“能自动做”不代表治理上“应该自动做”。

# 17. 50 个项目面试问题

## Q1. 你的项目解决了什么业务问题？

- **面试官关注点**：业务是否具体、可衡量。
- **标准回答**：它减少研发故障调查中跨监控、日志、知识库、Git 和项目管理系统的人工切换，把证据收集、根因假设、复盘和整改协同连成闭环。衡量指标是证据收集耗时、报告准备耗时、任务完成率和人工修改率，不先虚构收益百分比。
- **深入扩展**：目标用户是研发/SRE，首个范围是指定服务和时间窗口的只读调查，生产自动修复不在 MVP。

## Q2. 为什么选研发故障调查，而不是通用办公助手？

- **面试官关注点**：场景选择逻辑。
- **标准回答**：故障调查具备高价值、跨系统、证据驱动和路径不确定四个特点，能自然验证 Agent 的核心能力；结果又能通过已知根因和证据集客观评测。通用办公助手边界宽，容易退化为聊天与摘要 Demo。
- **深入扩展**：该场景还可与现有 RAG 项目形成“知识获取 + 任务执行”的组合叙事。

## Q3. 它为什么不是 ChatGPT 套壳？

- **面试官关注点**：系统工程证据。
- **标准回答**：核心 UI 是计划、步骤、证据、审批和报告，不是单一聊天框；后端有持久状态图、Skill Registry、MCP、Policy、幂等、Trace 和评测集。模型输出必须通过 Schema 与策略后才能产生动作。
- **深入扩展**：即使替换 LLM，任务状态、权限、工具和审计仍成立，说明系统价值不只来自提示词。

## Q4. 为什么这个任务需要 Agent？

- **面试官关注点**：是否滥用 Agent。
- **标准回答**：异常调查的下一步取决于中间观察，例如错误率上升后可能查日志、依赖 Trace 或近期变更，分支不能完全预先穷举。Agent 适合在有限候选中根据证据决定下一步。
- **深入扩展**：身份、审批、写入和终止仍由确定性 Workflow 负责。

## Q5. 为什么不用普通 Workflow？

- **面试官关注点**：技术选型权衡。
- **标准回答**：能固定的部分我确实使用普通 Workflow；只有意图、计划候选、Skill/Tool 候选和证据综合使用 LLM。若任务变成固定日报，我会改用普通 DAG，因为更便宜、可预测。
- **深入扩展**：选择 Agent 的门槛是运行时信息会改变合理路径，而不是流程步骤多。

## Q6. 为什么选择 LangGraph？

- **面试官关注点**：框架依赖是否合理。
- **标准回答**：需要显式 State、条件边、检查点、Interrupt 和恢复，LangGraph 与该控制模型匹配。它让步骤和状态可观察，适合人工审批和长任务；但权限、幂等、评测仍由业务层实现。
- **深入扩展**：若跨天任务、复杂补偿和大量非 LLM 活动占主导，可评估 Temporal 作为外层持久工作流。

## Q7. 什么叫“可控 Agent”？

- **面试官关注点**：控制点是否具体。
- **标准回答**：模型只能在权限过滤后的 Skill/Tool 中决策；计划有 Schema、步骤/预算上限和终止条件；写操作审批且幂等；所有结论有证据，所有动作有 Trace。控制权在 Runtime，不在 Prompt 自律。
- **深入扩展**：可控不等于完全固定，而是把概率性决策限制在可验证边界内。

## Q8. AgentState 为什么这样设计？

- **面试官关注点**：状态建模能力。
- **标准回答**：State 分开保存请求、意图、计划、步骤、证据、审批、错误和预算，节点只更新自己负责的字段。这样能检查完成度、支持恢复和调试；密钥与大体积原文只存引用。
- **深入扩展**：State schema 要版本化并提供迁移，否则运行中任务无法跨版本恢复。

## Q9. 为什么把 Plan Validation 单独做节点？

- **面试官关注点**：是否信任模型输出。
- **标准回答**：Planner 可能生成无效依赖、不可用 Skill 或错误风险等级。独立校验器用确定性规则检查 DAG、权限、预算和审批，只有通过的计划才能执行。
- **深入扩展**：校验失败可让模型按错误信息修复一次，仍失败则返回可解释错误，避免无限自修复。

## Q10. Planner 的输入输出是什么？

- **面试官关注点**：接口是否清晰。
- **标准回答**：输入是结构化 Intent、可用 Skill 摘要、用户权限、策略和预算；输出是 TaskPlan JSON，包含目标、步骤、依赖、skill_id、成功标准、风险和审批要求。Planner 不输出工具执行结果。
- **深入扩展**：只传摘要而非所有 Skill 全文，减少上下文和错误选择。

## Q11. 如何判断一个计划是好的？

- **面试官关注点**：计划评测。
- **标准回答**：先看合法性：Schema、无环、依赖存在、权限与风险正确；再看任务质量：必要步骤召回、冗余步骤、成功标准覆盖、可执行性。评测用专家标注计划和规则 grader 组合。
- **深入扩展**：计划文本相似度意义有限，更应比较依赖和能力覆盖。

## Q12. 什么时候允许重规划？

- **面试官关注点**：循环控制。
- **标准回答**：只有新证据使原计划不再适用、可恢复工具失败或 Evidence Gate 发现明确缺口时允许；权限拒绝不自动重规划绕过策略。最多两次，并受 token、工具和时长预算约束。
- **深入扩展**：每次重规划记录 reason 和 plan diff，便于评测与审计。

## Q13. Planner 幻觉出不存在的 Skill 怎么办？

- **面试官关注点**：目录约束。
- **标准回答**：Prompt 只提供 allowed skill IDs，JSON Schema 限制字段，Validator 再查 Registry。不存在或版本不可用的 Skill 直接拒绝计划，不允许模糊执行。
- **深入扩展**：可采用枚举动态生成或 tool search，但最终仍需服务端校验。

## Q14. Skill 和 Tool 的核心区别是什么？

- **面试官关注点**：概念边界。
- **标准回答**：Tool 是一个原子动作，比如搜索日志；Skill 是完成一类业务任务的可复用方法包，包含 Prompt、多个 Tool、约束、模板和验收。Skill 编排 Tool，Tool 不理解完整业务 SOP。
- **深入扩展**：同一个 `search_logs` 可以被故障调查、容量分析等多个 Skill 复用。

## Q15. Agent 如何发现和选择 Skill？

- **面试官关注点**：检索与权限。
- **标准回答**：Registry 先按租户、角色、风险和健康度硬过滤，再用关键词与向量召回候选，最后结构化重排。选中后才加载完整 Skill 指令；Policy 仍独立校验工具权限。
- **深入扩展**：记录 top-k、分数和最终选择，才能分析错选来自召回还是重排。

## Q16. 如何扩展一个新 Skill？

- **面试官关注点**：扩展是否低耦合。
- **标准回答**：新增目录与 manifest，声明输入输出、Prompt、工具、权限、预算和测试；通过 Schema、权限、安全与回归评测后注册。只要复用现有节点协议，通常无需修改主 Graph。
- **深入扩展**：需要新风险类型或新外部能力时，才扩 Policy/MCP，而不是把逻辑塞进 Prompt。

## Q17. Skill 如何版本化和回滚？

- **面试官关注点**：可复现性。
- **标准回答**：使用语义化版本，运行任务固定 `skill_id@version`，Trace 记录版本。新版本先离线评测和灰度；出现回归时 Registry 回滚默认版本，旧任务不热切换。
- **深入扩展**：破坏性输入输出变更升 major，并维护状态/结果兼容适配器。

## Q18. 为什么需要 MCP？

- **面试官关注点**：是否为技术而技术。
- **标准回答**：多个宿主需要以一致方式发现和调用监控、Git、文件能力；MCP 把 Runtime 与具体 SDK 解耦，并支持独立部署和统一契约。若只有三个本地函数且不会复用，直接函数调用更简单。
- **深入扩展**：本项目到阶段 5 才迁移 MCP，先证明业务闭环再引入协议层。

## Q19. MCP 与 Function Calling 有什么区别？

- **面试官关注点**：协议层次。
- **标准回答**：Function Calling 是模型输出函数名和参数的能力；MCP 是宿主与外部能力服务之间的连接、发现和调用协议。MCP Tool 最终也可暴露给模型做 Function Calling，但两者解决的问题层次不同。
- **深入扩展**：MCP 不自动解决业务授权，Function Calling 也不解决服务发现和传输。

## Q20. MCP Client 和 Server 分别负责什么？

- **面试官关注点**：调用链。
- **标准回答**：Server 声明 capability 并暴露工具/资源；Client 管理连接、初始化、工具列表、调用、超时取消和结果校验。Runtime 在 Client 之上增加身份、Policy、审批、Evidence 与 Trace。
- **深入扩展**：开发用 STDIO，企业远程用 Streamable HTTP 与 OAuth/Bearer。

## Q21. 为什么设计这几个 MCP Server？

- **面试官关注点**：服务边界。
- **标准回答**：Observability、Git、Workspace 分别对应证据、变更和交付物，权限域、可用性和扩缩容不同，适合独立边界。Knowledge Copilot 已有稳定 API，MVP 不强行包成 MCP。
- **深入扩展**：按业务域拆而非“一工具一服务”，避免部署碎片化。

## Q22. 如何保证 MCP 安全？

- **面试官关注点**：是否误信协议。
- **标准回答**：Server 使用最小权限身份和资源 allowlist；Client 校验 Schema、租户和输出；Runtime 再做审批、超时、出站控制与审计。工具注解只做提示，不作为授权依据。
- **深入扩展**：远程 Server 要验证来源、固定版本、限制重定向并防 SSRF；敏感结果先脱敏再进入模型。

## Q23. LLM 如何选择 Tool？

- **面试官关注点**：选择面与授权面。
- **标准回答**：先由 Skill 缩小工具命名空间，Registry 过滤权限与健康状态，模型在少量精确描述和 Schema 中提出调用。Policy Engine 最终 allow/approve/deny；所以模型只做语义选择，不做授权。
- **深入扩展**：工具多时采用分层 namespace/tool search，避免把所有 Schema 塞入上下文。

## Q24. Tool Schema 如何设计？

- **面试官关注点**：结构化与约束。
- **标准回答**：名称明确、描述含边界；参数使用 JSON Schema 限制类型、枚举、长度、时间、行数并禁用额外字段；重要结果定义 outputSchema。避免万能字符串参数。
- **深入扩展**：Schema 版本应做契约测试；描述变化也会影响模型选择，需要回归评测。

## Q25. 工具超时和重试怎么处理？

- **面试官关注点**：错误语义。
- **标准回答**：错误分 retryable、user_fixable、policy_denied、fatal。只读且可重放的瞬时错误指数退避重试；参数/权限错误不重试；达到上限后降级为部分结果或询问用户。
- **深入扩展**：MCP Server 级熔断和 bulkhead 防止一个依赖拖垮全部任务。

## Q26. 如何避免重复创建 Issue？

- **面试官关注点**：分布式副作用。
- **标准回答**：调用前生成由 task、step 和参数哈希组成的幂等键，并在数据库保存 pending/succeeded 与外部资源 ID。响应丢失时先按幂等键对账，不能直接重试创建。
- **深入扩展**：如果第三方 API 不支持幂等键，需要本地唯一约束和查询补偿，仍不能保证严格 exactly-once，只能实现有效一次语义。

## Q27. 审批机制如何设计？

- **面试官关注点**：HITL 是否真正安全。
- **标准回答**：审批卡展示动作、目标、关键参数、影响和证据；决定支持 approve/edit/reject。审批绑定用户、权限、参数哈希、task/step 和有效期，参数变化即失效；Graph 检查点可长期暂停并恢复。
- **深入扩展**：生产部署等高风险动作可以要求双人审批，但 MVP 直接不暴露该工具。

## Q28. Short Memory 和 Long Memory 有何区别？

- **面试官关注点**：生命周期与用途。
- **标准回答**：Short/Working Memory 服务当前任务执行与恢复，包含计划、步骤和审批；Long/Episodic Memory 保存经过筛选的历史任务摘要和明确偏好。企业文档知识属于独立 Knowledge Copilot，不塞进对话记忆。
- **深入扩展**：Redis 是热状态，不是长期真源；PostgreSQL 负责持久化。

## Q29. 什么时候读取 Memory？

- **面试官关注点**：是否无脑注入历史。
- **标准回答**：Intent 前读取策略和稳定偏好，Planning 前按服务/任务检索相关历史摘要，Tool 前读取检查点、审批与幂等记录。只加载与当前目标相关且通过 ACL 的最小内容。
- **深入扩展**：记录每次 Memory 召回理由和来源，便于查明历史上下文是否导致错误。

## Q30. 如何防止 Memory 污染？

- **面试官关注点**：长期错误传播。
- **标准回答**：只把结构化、脱敏、可归因的摘要写入长期 Memory；用户偏好需明确确认；失败结论标注未验证。检索内容当数据处理，不能改变系统策略。
- **深入扩展**：支持 TTL、删除、版本与反馈纠错，避免过期故障方案长期影响新任务。

## Q31. Agent 如何调用现有 RAG 项目？

- **面试官关注点**：服务契约与 ACL。
- **标准回答**：Knowledge Skill 调用 RAG Service API，传 query、tenant ACL 和过滤条件；返回 answer 与 document/chunk/source 引用，再转换为 Evidence。知识服务失败时主流程可降级，但报告明确缺失知识证据。
- **深入扩展**：Agent 不复刻 embedding/reranker；RAG 的检索版本也写入 Trace，便于复现。

## Q32. RAG 负责什么，Agent 负责什么？

- **面试官关注点**：项目边界。
- **标准回答**：RAG 负责从企业文档中找到可信、可引用的知识；Agent 负责基于目标决定何时查知识、同时收集实时证据、形成计划并执行动作。知识是观察，行动由 Agent 治理。
- **深入扩展**：RAG 的低分结果不会自动变成工具参数，仍要经过 Evidence/Policy。

## Q33. 如何防御知识库 Prompt Injection？

- **面试官关注点**：间接注入。
- **标准回答**：检索文档明确包裹为 untrusted data；系统指令与工具策略不接受文档覆盖；外部内容不能新增工具或改变权限；恶意样本加入评测。关键动作仍由参数策略和审批决定。
- **深入扩展**：对输出引用做来源验证，并限制文档内容进入工具参数的字段与长度。

## Q34. 为什么需要多模态？

- **面试官关注点**：真实价值。
- **标准回答**：故障现场经常只有监控或日志截图，多模态减少手工转录并保留时间/错误码。范围仅限结构化提取，不做无关图片理解，所以是业务输入适配，不是炫技。
- **深入扩展**：先用文本主链路完成 MVP，再加截图，保证视觉不是核心依赖。

## Q35. 视觉模型识别错了怎么办？

- **面试官关注点**：不确定性处理。
- **标准回答**：输出字段级置信度和来源区域，低置信字段在 UI 高亮让用户确认；原图保留受控引用；关键时间/服务名还可与后端数据交叉验证。
- **深入扩展**：视觉评测看字段准确率和关键错误召回，不只看整体描述是否自然。

## Q36. 身份与权限怎么做？

- **面试官关注点**：企业接入。
- **标准回答**：Gateway 从 SSO/JWT 获取真实身份，构造不可由前端伪造的 ExecutionContext；Policy 使用 RBAC 决定角色能力，ABAC 决定租户、仓库、服务和环境范围。MCP 使用下游最小权限服务身份或受控 on-behalf-of token。
- **深入扩展**：权限在计划前过滤一次、工具调用前再校验一次，防 TOCTOU 与计划漂移。

## Q37. 如何做多租户隔离？

- **面试官关注点**：数据层细节。
- **标准回答**：所有任务、Memory、Evidence 和审计记录带 tenant_id；数据库使用行级策略/强制过滤；对象存储按租户前缀与密钥隔离；向量检索先做 ACL 过滤。跨租户测试属于发布门槛。
- **深入扩展**：Prometheus 不用 tenant/user 高基数标签，租户明细放受控日志与 Trace。

## Q38. 如何做全链路可观测性？

- **面试官关注点**：能否定位模型/工具/系统问题。
- **标准回答**：Trace 按 task→node→model/tool→policy/approval 建层级，记录版本、耗时、token、错误与 Evidence；Prometheus 统计任务、工具、重规划、审批等待和延迟；审计日志记录不可抵赖的写动作。
- **深入扩展**：敏感输入输出默认脱敏或关闭采集，Trace ID 不作为指标标签。

## Q39. 你最看重哪些评测指标？

- **面试官关注点**：是否与业务和风险匹配。
- **标准回答**：首先是未授权写操作为 0 和引用正确；其次是端到端任务完成率、关键证据覆盖、工具/参数准确率与恢复率；最后才是语言表达、延迟和成本。指标按风险优先级而非只看平均分。
- **深入扩展**：安全关键用例用硬门槛，普通质量指标用基线和置信区间判断回归。

## Q40. Golden Set 怎么构建？

- **面试官关注点**：数据与覆盖。
- **标准回答**：从脱敏故障类型构造输入、允许证据、预期关键步骤、禁止动作和完成标准；覆盖正常、歧义、冲突证据、工具故障、越权、注入、审批拒绝和恢复。每条用例标注可程序判断的字段。
- **深入扩展**：按线上失败聚类持续补集，但要版本化并避免把测试答案泄漏进 Prompt。

## Q41. 如何保证 Citation 可靠？

- **面试官关注点**：引用是否只是格式。
- **标准回答**：Evidence Store 保存 source_uri、采集时间、内容哈希和原始引用；最终答案只能引用存在且 ACL 允许的 Evidence ID。Evidence Gate 检查关键结论覆盖和引用可访问性。
- **深入扩展**：因果结论需区分支持证据和反证；有相关性不等于已证明根因。

## Q42. Reflection 会不会无限循环？

- **面试官关注点**：终止机制。
- **标准回答**：不会。Reflection 只返回 pass/replan/fail，重规划最多两次，并同时受总步骤、工具次数、token 和时长预算；达到上限输出部分结果与未完成项。
- **深入扩展**：记录每次缺口与 plan diff，可发现某类用例是否长期卡住。

## Q43. 任务失败后如何恢复？

- **面试官关注点**：持久化与重放安全。
- **标准回答**：每个节点完成后写 PostgreSQL Checkpoint；重启用 task/thread ID 恢复最近状态。已完成读步骤不重复，写步骤查询幂等记录与外部资源 ID；不可确定状态进入人工对账。
- **深入扩展**：恢复测试要包含节点前、节点中、外部成功但响应丢失三个故障点。

## Q44. 系统如何扩展并发？

- **面试官关注点**：运行模型。
- **标准回答**：API 无状态，任务放队列/worker；不同 task 并行，同一 task 的无依赖只读步骤有限并行，写步骤串行加锁。MCP Client 按服务连接池、限流和 bulkhead，数据库按 task/tenant 分区与索引。
- **深入扩展**：先用负载测试找到模型、MCP 或数据库瓶颈，再扩，不为简历预先上复杂 Kubernetes。

## Q45. 如何选择和路由模型？

- **面试官关注点**：是否硬编码单模型。
- **标准回答**：按任务能力与风险路由：结构化 Intent/轻量分类用低延迟模型，复杂规划/证据综合用强推理模型，视觉用 Vision Provider；所有模型必须通过对应评测基线。Gateway 统一超时、fallback 和版本记录。
- **深入扩展**：高风险动作不因更强模型而取消审批；fallback 也不能降低安全策略。

## Q46. 如何控制成本？

- **面试官关注点**：生产运营意识。
- **标准回答**：渐进式加载 Skill/Tool，先规则过滤再调用模型；压缩历史上下文，只传 Evidence 摘要与引用；按节点使用不同模型；设置 token、工具数、重规划和时长预算，并记录单任务成本。
- **深入扩展**：缓存只用于确定且权限一致的读结果；带用户/时间敏感数据要谨慎设置键与 TTL。

## Q47. 为什么不用多 Agent？

- **面试官关注点**：是否追热点。
- **标准回答**：MVP 的任务可以由一个受控 Runtime 加多个 Skill 完成，多 Agent 会增加上下文同步、责任边界、调试和成本。只有需要独立权限域、并行专家或长期自治时才考虑拆分。
- **深入扩展**：若未来增加安全审核 Agent，也应通过结构化交接和统一 State，而非自由群聊。

## Q48. 如何从 Demo 走向生产？

- **面试官关注点**：落地路径。
- **标准回答**：先限定一个只读闭环和可重复评测；再补状态持久化、错误语义、权限审批、幂等、Trace 和数据治理；之后灰度真实连接器和小范围用户，基于失败数据迭代。Docker 化只是部署形式，不等于生产化。
- **深入扩展**：上线前需要 owner、SLO、runbook、回滚、审计和事故响应流程。

## Q49. 当前项目最大的限制是什么？

- **面试官关注点**：是否诚实且有边界。
- **标准回答**：MVP 基于脱敏/模拟系统，不能证明真实企业网络、权限和数据规模下的所有行为；根因分析仍是证据支持的假设，不保证自动诊断正确；生产变更不自动执行。这些限制在 UI 和报告中明确展示。
- **深入扩展**：下一步优先接一个真实只读监控源并扩大故障集，而不是先增加更多 Agent。

## Q50. 如果再做一个版本，你会优先改什么？

- **面试官关注点**：迭代判断。
- **标准回答**：根据评测和 Trace 选择最高频失败：若计划遗漏就优化 Skill 元数据与 Planner；若工具参数错就收紧 Schema/增加参数化工具；若证据不足就改查询策略。技术路线由失败分布驱动，不预设一定上多 Agent。
- **深入扩展**：工程上会优先补真实只读连接器、在线反馈闭环和发布回归门禁，再考虑更广业务场景。

## 18. 面试回答检查表

每次回答项目问题前快速检查：

1. 是否先说了业务目标，而不是框架名？
2. 是否说明了模型决策与系统授权的边界？
3. 是否给出输入、输出、失败模式和验收？
4. 是否承认 MVP 限制，没有把目标指标说成实测结果？
5. 是否能指向仓库中的代码、测试、Trace 或评测报告？

最有说服力的回答结构：**结论 → 本项目如何实现 → 为什么这样权衡 → 如何验证。**
